# UAT Test Data Plan

**Date:** 2026-09-16. Defines the data UAT execution should use. **No production data — `server/
db.json` — is ever used for UAT.** UAT runs exclusively against a dedicated, isolated instance.

## Environment

A dedicated UAT instance, separate from both production (`server/db.json`, port 4001) and this
engagement's own disposable engineering-test scratch instance (`APP_ENV=test`, port 4100, used for
DEF-2026-001/CR-2026-001 verification). Recommended: a fresh, clean `APP_ENV=test` instance,
provisioned fresh for the UAT cycle, reset via the existing `POST /api/test/reset` mechanism (already
proven safe and isolated — confirmed fail-closed against a production-shaped target by
`erp_059c_production_isolation_tests.js`, 10/10).

**Do not reuse the engineering scratch instance's accumulated data for UAT** — it already carries
hundreds of engineering-test transactions (from the 525-document stress runs) that would confuse a
business user reading the screens. Start UAT from a genuinely clean `/api/test/reset`.

## Naming convention

Every UAT-created record should be identifiable at a glance:

- Customers/Prospects: `UAT-<Business Scenario Name>` (e.g., "UAT-Kochi Villa Fitout")
- Projects: inherit the Quotation's own naming (`<Prospect> — <Quotation No>`) — already
  self-identifying, no extra tagging needed
- Suppliers: `UAT-Supplier-<n>` if a new one is needed, or reuse the existing seeded `VEND-1..7`
- Materials: reuse the existing seeded material master (`MAT-1` Plywood 18mm, `MAT-2` Laminate, etc.)
  — do not invent new materials unless a scenario specifically needs one
- Narrations on manual Journal Vouchers: prefix with `UAT —` (e.g., "UAT — opening stock adjustment")

## Users / Roles

Use the existing seeded UAT-dedicated accounts (`uat_admin`, `uat_finance`, `uat_accountant`,
`uat_purchase`, `uat_sales`, `uat_pm`, `uat_estimator`, `uat_site`, `uat_ceo`, `uat_viewer` — added
Phase 36 specifically for shareable UAT use, see `sap_architecture_lab.md` Revision 38). These are
already distinct from both the engineering test users (`admin`/`ceo`/`finance1`/etc.) and any real
Appletree staff account, so UAT actions are never confusable with either engineering testing or real
production activity.

| Inventory | Populated organically via GRN/Site Material flows, not pre-seeded with arbitrary stock |

| Installation/Handover | At least one full, real chain per Scenario Group G/H |
| Financial Transactions | Organically generated by the above chains — Invoice, Receipt, Supplier Bill, Supplier Payment, at least one Journal Voucher |

## What NOT to do

- Do not copy, import, or reference any real Appletree customer, vendor, GSTIN, PAN, Aadhaar, bank
  account, or employee data into the UAT instance.
- Do not point the UAT instance's `DB_PATH` at `server/db.json` under any circumstance.
- Do not run `/api/test/reset` or any other destructive endpoint against a server whose
  `/api/system/environment` does not report `appEnv:"test"` — this is the ERP-059C rule, permanent
  and non-negotiable.
- If a UAT tester needs to demonstrate a "before this fix" comparison for DEF-2026-001 or any other
  closed defect, do NOT revert the fix in a shared UAT instance — the before/after evidence already
  exists in the closed defect's own test report; re-breaking a fix to "show" the old behavior risks
  someone forgetting to re-apply it.

## Reset between UAT cycles

`POST /api/test/reset` (Admin only, `APP_ENV=test` only) restores the clean seed instantly — use this
between distinct UAT cycles or if a tester's exploratory testing leaves the dataset in a confusing
state, rather than manually cleaning up individual records.
