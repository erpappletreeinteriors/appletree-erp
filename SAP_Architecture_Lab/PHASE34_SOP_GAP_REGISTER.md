## New defect found and fixed during this phase's own self-test

**`dispatchToJobWorker()` originally posted an unrecognized inventory movement type (`'JobWorkIssue'`) for the warehouse-side reduction.** `getStockLevel()`'s reduce() only recognizes `Receipt`/`TransferIn`/`Issue`/`TransferOut`/`Return`/`Adjustment` — the unrecognized type silently no-oped, so warehouse stock was never actually reduced by a job-work dispatch while the job-worker-held stock was correctly credited via the new `JobWorkReceipt` type. This meant the SAME material would appear to exist BOTH still in the warehouse and at the job worker simultaneously — a genuine double-counting defect. Found by this phase's own live test suite (not by manual review), root-caused in minutes by checking `getStockLevel()`'s actual recognized type list, fixed by reusing the EXISTING `'Issue'` type for the warehouse-side movement (the exact same pattern `issueToSite()` already used for the Phase 33 site subledger). Re-verified via: the original failing test now passing, a dedicated 120-dispatch/8-job-worker/5-material stress test showing exact reconciliation with zero drift, and the full 52-file + Phase 33's 55-test regression suite still green.
