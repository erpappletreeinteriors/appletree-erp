# Appletree ERP — Screen-by-Screen UI Audit (111 tabs)

**Source:** `SAP_Architecture_Lab/client_secure/index.html` (single HTML file, 111 `<div class="tab">` sections, one `renderXxx()` JS function per tab, dispatched from a `fns{}` map in `renderTab()`).

**Navigation model (applies to every row below):** Nav is two-level and identical in structure everywhere — a flat row of ~17 top-level group buttons (`NAV_GROUPS`, `#mainNav`) and, under it, a second flat row of subnav buttons for the tabs in that group (`#subNav`, built by `selectGroup()`). Clicking a subnav button calls `selectTab()` → shows `#tab-<id>` and calls that tab's `render*()`. There is no dropdown/mega-menu, no search-driven nav, and no breadcrumb; cross-tab links (`goto('GROUP','tab')`) exist only as ad hoc "→" links inside specific screens. Below, "Nav" is written as `Top nav: GROUP ▸ Label`.

## Cross-cutting observations

- **No table in the app has client-side pagination, and only 3 have server-side pagination.** Every list screen (Leads, Projects, POs, GRNs, Material Requests, Job Cards, GL, Trial Balance, etc.) renders its *entire* result set into one `<table>`. Only Stock Movement Ledger (`tab-movements`), Journal Register (`tab-jereg`), and Audit Log (`tab-audit`) implement real `page`/`pageSize`/`hasMore` paging — everywhere else, a growing dataset just grows the DOM.
- **Search/filter exists only on a handful of screens, inconsistently.** `filterRows()` (a client-side substring filter over `data-search` attributes) is wired up on Leads, Projects, Purchase Orders, GRNs, Audit Log, and the Cash Control Exceptions sub-table of Compliance Reports — roughly 6 of 111 screens. Everywhere else (Service Tickets, AMC Contracts, Job Cards, General Ledger, Chart of Accounts, etc.) there is no way to filter a list except scrolling.
- **The same "raw CSV paste into a textarea" import pattern is independently implemented 5 times** (Master Data Import, Opening Balances, Bank Reconciliation, ICICI Bank Import, Controlled Journal Import) rather than as one shared component — each has its own template/preview/history logic, and none supports actual file upload.
- **`window.prompt()`/`confirm()` chains are used throughout as a substitute for in-page forms**, for actions as consequential as capitalizing a fixed asset (4 chained prompts), recording a service-visit diagnosis (5 chained prompts), scrapping job-work material, or approving discounts. This bypasses the app's own form styling entirely and gives no client-side validation, inline error messages, or ability to review before submitting.
- **Status is shown only as a plain `<span class="pill">` and color-coding is applied inconsistently.** Many render functions add `good`/`bad` classes for terminal states (e.g. GRN weighment, Snags severity, Warranty status) but many others (Material Requests, RFQs, Purchase Requisitions, Job Cards machine status, Tasks) render the same `pill` class with no color logic at all, so "Draft" and "Approved" look identical on those screens.
- **Line-item editors (add/remove row UIs) are reimplemented independently at least 9 times** — Estimation & Costing cost lines, Material Requirements, Material Issues, BOM lines, New JE lines, Labour & Wages, Purchase Requisition lines, Job Work dispatch lines — each keeping its own ad hoc `window._xxxLines` global array and its own `add`/`remove`/re-render trio of functions, rather than one shared component.
- **Bulk-create actions loop sequential POST requests in the browser** (Material Requirements, Material Issues, Labour & Wages, Purchase Requisitions) with no batch endpoint — a failure partway through a 10-row submission requires the user to parse a combined "N created / M failed: ..." message to figure out which rows need re-entry.
- **No breadcrumb or "you are here" trail exists anywhere in the app** beyond the two active-nav-button highlight states; the only wayfinding aid across tabs is ad hoc `goto('GROUP','tab')` doclinks embedded inside specific screens (e.g. Project 360 → Procurement, Customer Profitability → Project 360).
- **Loading and empty states are inconsistent.** Some screens set a literal `"Loading…"` placeholder before their first fetch resolves (Job Cost Sheet, Balance Sheet); most simply leave the container blank until the `await` completes, with no spinner. Empty-state messaging is similarly ad hoc — many tables use a styled `<div class="empty">`, but others (Machines, Chart of Accounts, GL) just render zero `<tr>`s under the header with no message at all.
- **N+1 network-call patterns appear in several render functions**: `renderStock()` fires one GET per material×warehouse pair, `renderTickets()` fires one extra GET per open ticket for SLA status, `renderAMC()` fires one extra GET per contract for its revenue schedule, and `renderEstCost()` fires one extra GET per estimation request for its costing versions — all inside `for` loops with no batching, and no loading indicator while they run.
- **Several screens mix distinct business domains on one tab** with no internal sub-navigation: Site Material (5 sections: sites, MRS, delivery challans, consumption, reconciliation), Finance SOP Configuration (6 unrelated policy domains), Compliance Reports (4 unrelated reports), and Users & Roles (routine user admin sitting directly above a destructive "wipe all UAT data" control).
